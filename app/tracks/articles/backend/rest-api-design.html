API ای که شش ماه بعد هم خوانا بماند

ن نیما رستمی ۱۰ مهر ۱۴۰۵ ۷ دقیقه مطالعه

بدترین APIها آن‌هایی نیستند که کند هستند؛ آن‌هایی هستند که هر endpoint یک ساز می‌زند: یک‌جا /getUsers، جای دیگر /user/create و جای سوم /delete_task. شش ماه بعد، خود نویسنده هم باید حدس بزند. راه‌حل، یکنواختی قراردادی است.

منابع، نه فعل‌ها

در REST، URL نام یک منبع است (اسم، جمع) و فعلِ کار را متد HTTP می‌گوید. این تقسیم کار باعث می‌شود مسیرها قابل حدس باشند و کلاینت بدون خواندن مستندات، ساختار را بفهمد.

GET    /api/tasks          # فهرست
POST   /api/tasks          # ایجاد
GET    /api/tasks/42       # یک تسک
PATCH  /api/tasks/42       # ویرایش جزئی
DELETE /api/tasks/42       # حذف

کدهای وضعیت، زبان مشترک

  • 200 برای موفقیت معمولی، 201 برای ایجاد منبع.
  • 400 خطای ورودی کاربر، 401 نبود احراز هویت، 403 نبود دسترسی.
  • 404 منبع نیست، 409 تعارض (مثلاً ایمیل تکراری).
  • 500 یعنی تقصیر سرور است؛ هرگز خطای کاربر را 500 برنگردان.
نکتهٔ منتور: بدنهٔ خطا را هم استاندارد کن: { "error": { "code", "message", "fields" } } تا کلاینت بتواند خطا را به‌صورت ماشین‌خوان پردازش کند.
بازگشتصفحهٔ مسیر بک‌اند مقالهٔ بعدیJWT: سه اشتباه رایج که هنوز تکرار می‌شوند
